You are the lead full-stack engineer responsible for implementing a complete web application named:

ProView — Course Project Submission and Peer Review Platform

Your task is to implement the entire system end-to-end until it is ready for deployment, but DO NOT deploy it to any external hosting provider. Stop only after the application can be built and run locally in production mode, all required migrations and seed data work, and all automated checks pass.

Do not stop after scaffolding.
Do not leave core functionality as TODOs.
Do not create fake/mock implementations for core business processes.
Do not replace difficult requirements with simplified placeholders.
Make reasonable engineering decisions when a minor detail is unspecified and document the decision.

If an existing repository is present, inspect it first and preserve useful existing work. If the repository is empty, initialize it from scratch.

============================================================
1. SYSTEM PURPOSE
============================================================

ProView is NOT a general-purpose Learning Management System.

It is a specialized platform for managing the lifecycle of university course projects:

course setup
→ project groups
→ project submission
→ peer/instructor review
→ conflict-of-interest handling
→ rebuttal
→ final submission
→ textual similarity checking
→ grading
→ cross-semester archive

The primary users are:

1. Student
2. Instructor
3. Administrator

The system must focus on project submission and structured review. Do not add unrelated LMS functionality such as lectures, quizzes, certificates, payments, events, or general-purpose messaging.

============================================================
11. REVIEWER ASSIGNMENT
============================================================

Support two reviewer types:

1. Instructor reviewer
2. Peer project-group reviewer

Peer review is group-to-group.

A reviewer assignment targets a reviewer ProjectGroup.

Members of that reviewer group may collaborate on one review draft.

The submitted review records which student actually submitted it on behalf of the group.

ReviewerAssignment statuses:

ASSIGNED
IN_PROGRESS
COI_REQUESTED
REASSIGNMENT_APPROVED
REASSIGNED
SUBMITTED
CANCELLED

Implement both:

- manual assignment by instructor
- automatic peer reviewer assignment

Automatic assignment must:

- never assign a group to itself
- reject conflicts detectable from system data
- balance reviewer workload as evenly as possible
- avoid duplicate assignment of the same reviewer group to the same submission
- avoid reciprocal assignments A→B and B→A when alternatives exist
- produce deterministic and explainable results

Place assignment logic in a dedicated domain service.

Add tests for the assignment algorithm.

- reason

Statuses:

============================================================
17. FINAL REPORT AND COOPY WORKFLOW
============================================================

COOPY is NOT an API integration.

Do not invent a REST API for COOPY.

Treat it as a manual asynchronous external process.

SimilarityCheck statuses:

PENDING
SUBMITTED_EXTERNALLY
COMPLETED
FAILED
WAIVED

Workflow:

1. Final report is submitted.
2. SimilarityCheck is created with PENDING.
3. Authorized Instructor/Admin obtains the report.
4. Staff manually submits it to COOPY outside the system.
5. Staff marks it SUBMITTED_EXTERNALLY.
6. COOPY result is received externally.
7. Staff records:
   - similarity percentage if available
   - result date
   - notes
   - optional result PDF
8. Status becomes COMPLETED.

Also allow FAILED and WAIVED with mandatory reason.

The system must make it clear that:

- this check concerns textual similarity
- similarity does not automatically mean plagiarism
- ideas, diagrams, project topics, and conceptual similarity are not automatically judged by the system
